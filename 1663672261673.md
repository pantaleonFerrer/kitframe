## 1. Product scope

### 1.1 What this platform is
Kitframe is a multi-brand platform that takes a brand's product data and creative production process and runs it through four layers: structured data, coordinated team workflow, automated visual production, and quality-gated generative content. FC Barcelona is the first brand configured in the system; the data model is multi-tenant throughout, so onboarding a second brand later is a configuration task, not a rebuild. Kitframe currently operates under the Gathered brand (visual identity, domain, and go-to-market); the architecture below does not assume that continues, so a future separation is a branding and deployment change, not a re-architecture.

### 1.2 Complete feature scope
- Multi-brand account structure: per-brand taxonomy schema, translation glossary, golden set, channel specs, and Shopify connection.
- Technical sheet ingestion (PDF/XLSX/image) with LLM-based structured extraction, confidence scoring per field, and a human review workflow for low-confidence fields.
- SEO copy and multi-locale translation generation (Spanish, Catalan, English), respecting a brand glossary of do-not-translate terms.
- Deterministic multi-channel export: sizes, ratios, formats, color profile, metadata, and filename convention, per channel, per brand.
- A five-step (brand-configurable) workflow board — Technical sheet → Visual production → Retouch & QC → Approval → Published — with per-team filtering, due dates, and bottleneck alerts.
- Batch background removal, ghost mannequin processing, and simple retouch for product-only and on-model shots.
- Asset intelligence: automatic tagging, embedding-based semantic search, and reuse/duplicate detection across the asset library.
- Golden-set-based automated QC scoring (color fidelity, logo/crest position, texture, proportions, resolution) with configurable thresholds and a human review queue for borderline results. Nothing is published without a passing QC run.
- A provider-agnostic image and video generation abstraction with at least one fully integrated real provider, plus a benchmarking harness to compare providers against the same golden set on quality, cost, and latency.
- A two-stage avatar pipeline: identity training from a small reference photo set, and independent pose control, so the same digital model can be reused consistently across campaigns.
- Deterministic crest/logo compositing: the generative model never draws the club crest; the real crest asset is warped and composited onto the generated image using detected keypoints, then that composited result is what goes through QC.
- Hard-gated rights management for any generation involving a real, identifiable person (e.g. a player). This is enforced in the backend before any generation job is even enqueued, not just hidden in the UI.
- Full Shopify integration: product and metafield publish, webhook-based sync, scheduled inventory reconciliation, duplicate protection, and an explicit staging-to-live-store promotion action.
- Internal notification system: per-user, per-event-type channel and frequency preference, quiet hours, digest batching, and delivery tracking.
- Full audit trail on every state-changing action in the system.
- Role-based access control, brand-scoped, with an admin console for user and permission management.
- A creative briefing assistant: notes in, a structured brief draft out, with a human validation step before it goes to the creative team.
- A complete, production-grade frontend implementing every screen in Section 15, built on the design system in Section 13.

### 1.3 Explicitly out of scope for this specification
These are deliberate scope boundaries, not deferred phases — they are not part of this build:
- Single sign-on (SAML/OIDC). Email/password auth is the complete auth system specified here.
- Multi-region deployment. Single EU region.
- Autoscaling infrastructure. Fixed replica count per service (Section 22).
- A native mobile app. Responsive web only.
- A public API for third-party developers. This platform is internal/agency-facing.

If any of these become necessary later, they are new specification work, not something this document leaves half-built.

## 3. Architecture

### 3.1 Service boundaries
- **Go core service**: the only writer to Postgres. Owns business rules, state transitions, auth, Shopify integration, notification dispatch, audit logging.
- **Python AI service**: stateless compute. Receives everything it needs in the request (signed URLs, schema, parameters); returns a result; never touches the database.
- **Frontend**: talks only to the Go service, never directly to the AI service, even for AI-triggered features — the Go service always persists the result so there is one source of truth for what happened.

### 3.2 Canonical request flow (illustrated with QC scoring; every AI-touching feature follows this shape)
1. Frontend calls `POST /assets/:id/run-qc`.
2. Go service loads the asset and the relevant golden set entry, calls the Python service's `/qc-score` with signed URLs.
3. Python service returns the score breakdown. Go service writes the `qc_runs` row, updates `assets.qc_status`, writes an `audit_log` row, triggers a notification if the result is `needs_review`, and returns the result to the frontend.

### 3.3 Deployment topology
```
                     ┌─────────────┐
   users ──────────▶ │   Next.js   │
                     └──────┬──────┘
                            │ HTTPS (JWT)
                     ┌──────▼──────┐
                     │  Go core    │───────┐
                     │  service    │       │ HTTPS (internal, private network)
                     └──────┬──────┘       ▼
                            │        ┌─────────────┐
                            │        │ Python AI   │
                            │        │ service     │
                            │        └──────┬──────┘
                     ┌──────▼──────┐        │
                     │ PostgreSQL  │        ▼
                     └─────────────┘  ┌──────────┐
                     ┌─────────────┐  │  Ollama   │
                     │ Object store│  └──────────┘
                     └─────────────┘
```
Only the frontend and the Go service's public API are internet-facing, both behind TLS termination at the load balancer. All other traffic stays inside the private network.

### 3.4 Async job architecture
Any operation that can take more than ~2 seconds — extraction, batch export, QC scoring, generation, avatar training — is a job, not a synchronous request. The Go service enqueues a typed `river` job; a worker pool (the same Go binary run with a `--worker` flag, deployed separately from the API process) processes jobs, calls the AI service, writes results, triggers notifications. The frontend tracks job status via `GET /jobs/:id` or the SSE stream. Every job type defines a retry policy (max attempts, backoff) and surfaces permanently failed jobs in an admin dead-letter view.

## 4. Data model

Implement as versioned SQL migrations (`golang-migrate` or `sqlc`'s migration tooling — pick one, do not mix). UUID primary keys throughout. Every table has `created_at`, `updated_at` (`timestamptz`, default `now()`) unless noted otherwise. Every migration is forward-only in any deployed environment; a mistake is corrected with a new forward migration, never a down-migration run against real data.

### 4.2 Indexing
- Every foreign key indexed (Postgres does not do this automatically).
- `products (collection_id, status)` composite — the board's primary query.
- `assets (product_id, qc_status)` composite.
- `asset_embeddings` uses `ivfflat`; rebuild after bulk imports rather than relying on incremental updates alone.
- `audit_log (entity_type, entity_id, created_at)` composite for the entity history view.

- [ ] Full schema applied via versioned migrations, single command to run, `pgvector` enabled and tested with a real nearest-neighbor query.

## 5. Auth & permissions

### 5.1 Auth flow
- `POST /auth/login` — email + password, returns an access token (15 min expiry) and sets an httpOnly refresh token cookie (30 day expiry).
- `POST /auth/refresh` — exchanges a valid refresh token for a new access token.
- `POST /auth/logout` — invalidates the refresh token server-side (revocation list or per-user token version).
- Passwords hashed with `argon2id`, minimum 12 characters enforced client- and server-side.
- Login rate-limited: 5 attempts per email per 15 minutes, 20 per IP per 15 minutes, clear `429` response with a `retry_after` value.

### 5.2 RBAC matrix
| Action | Viewer | Editor | Admin | Owner |
|---|---|---|---|---|
| View board, product detail | ✓ | ✓ | ✓ | ✓ |
| Edit structured data fields | | ✓ (own team's step only) | ✓ | ✓ |
| Advance workflow step | | ✓ (own team's step only) | ✓ | ✓ |
| Run QC | | ✓ | ✓ | ✓ |
| Approve / override QC | | | ✓ | ✓ |
| Publish to Shopify | | | ✓ | ✓ |
| Manage golden set | | | ✓ | ✓ |
| Manage rights records | | | ✓ | ✓ |
| Manage users / roles | | | | ✓ |
| Manage brand settings (taxonomy, glossary, channel specs) | | | | ✓ |

Enforce server-side via middleware driven by a declared permission requirement per route (`requirePermission("qc.approve")`), not scattered `if role == "admin"` checks scattered through handlers — the matrix above should be readable directly from one file in the codebase.

### 5.3 Definition of Done
- [ ] Every RBAC matrix cell has a corresponding negative test.
- [ ] Refresh token rotation tested, including the revoked-token-rejected case.
- [ ] Login rate limiting tested with an automated script.

### 6.1 Error contract
Every error response has the same shape:
```json
{ "error": { "code": "invalid_step_transition", "message": "Cannot move from 'approval' to 'visual_production'", "details": {} } }
```
Error codes are constants defined in one place. The frontend matches on `code`, never on `message` text.

### 6.2 Step transition rules
Valid transitions only: `technical_sheet → visual_production → retouch_qc → approval → published`. No skipping. Entering `approval` requires every asset on the product to be `qc_status = pass`, or an explicit admin override logged in `audit_log`. Entering `published` calls the Shopify integration and is only reachable from `approval`.

### 6.3 Definition of Done
- [ ] Full OpenAPI spec generated and validated in CI against the actual route table — an undocumented route fails the build.
- [ ] Pagination tested on at least one endpoint seeded with 500+ rows.
- [ ] Error contract used on 100% of error responses.
- [ ] Step transition rules tested for every valid and invalid transition pair.

## 7. AI service — architecture

Stateless FastAPI service. Every endpoint enforces a request timeout (30s for extraction/copy generation, 60s for image operations), logs with a request ID that ties back to the originating Go service call, and exposes Prometheus metrics (request count, latency histogram, error count) per endpoint.

## 8. AI service — endpoints

### 8.1 Extraction
```
POST /extract
Body: { "source_document_url": string, "taxonomy_schema": object }
Returns: {
  "fields": { "<key>": { "value": any, "confidence": number } },
  "needs_review_fields": string[]
}
```
Convert the document to text/markdown (PDFs) or pass as vision input (scanned/image documents) to the Ollama-hosted extraction model. Generate the structured-output prompt programmatically from `taxonomy_schema` — never hand-write a prompt that has to be edited every time a field is added. Default model: a strong open-weight multilingual model in the 32B+ class, validated specifically against real Catalan/Spanish technical sheets before being finalized (Section 29). Model name is an environment variable, never hardcoded.

### 8.2 SEO + translation
```
POST /generate-copy
Body: { "product": { structured_data fields }, "locales": ["es","ca","en"], "glossary": object }
Returns: {
  "seo": { "title": string, "meta_description": string, "keywords": string[] },
  "translations": { "es": {...}, "ca": {...}, "en": {...} }
}
```
Apply the brand glossary as hard post-generation string substitutions for any term marked `do_not_translate`, so proper nouns and technical terms are never left to the model's judgment.

### 8.3 Image processing
```
POST /process-image
Body: { "asset_url": string, "operation": "remove_background" | "ghost_mannequin" | "retouch" }
Returns: { "processed_url": string }
```

### 8.4 QC scoring — the module that matters most
```
POST /qc-score
Body: { "asset_url": string, "golden_set_image_id": string }
Returns: {
  "color_score": number,
  "logo_position_score": number | null,
  "resolution_score": number,
  "overall_score": number,
  "result": "pass" | "needs_review" | "fail",
  "detail": { ... per-check breakdown ... }
}
```
- `color_score`: convert both images to Lab color space, sample the dominant garment region (exclude background), compute Delta-E 2000 against the golden set reference, normalize to 0..1 with a documented curve (comment the curve in code — no unexplained magic numbers).
- `logo_position_score`: computed only when the golden set entry has a `logo_bounding_box`. Detect the logo region on the candidate (template-match or a small classifier). A genuinely uncertain detection must resolve to `needs_review`, never a silent pass.
- `overall_score`: weighted average with color weighted highest; because crest fidelity has zero tolerance, any near-miss on `logo_position_score` forces `needs_review` regardless of what the weighted average alone would say.
- Thresholds are config, not hardcoded: `pass` ≥ 0.90 overall AND no individual check below 0.75; `fail` < 0.60 overall; everything else `needs_review`.

### 8.5 Avatar identity training
```
POST /train-avatar-identity
Body: { "reference_asset_urls": string[] }
Returns: { "identity_profile_ref": string }   (async job; this endpoint is called by a worker, not directly by a request-response HTTP call from the UI)
```

### 8.6 Image and video generation — provider abstraction
```
POST /generate-image
Body: { "provider": string, "prompt": object, "reference_assets": string[], "avatar_identity_ref": string | null, "pose_skeleton_url": string | null }
Returns: { "generated_url": string, "provider_used": string, "cost_usd": number | null, "latency_ms": number }
```
```python
class GenerationPrompt(BaseModel):
    garment_asset_url: str
    avatar_identity_ref: str | None
    pose_skeleton_url: str | None
    scene_description: str
    output_type: Literal["image", "video"]

class GeneratedAsset(BaseModel):
    url: str
    provider: str
    cost_usd: float | None
    latency_ms: int

class GenerationProvider(Protocol):
    key: str
    def generate(self, prompt: GenerationPrompt) -> GeneratedAsset: ...
    def supports(self, output_type: str) -> bool: ...

PROVIDERS: dict[str, GenerationProvider] = {
    "mock": MockProvider(),   # deterministic fixture output, used only in tests/CI, never in a real request path
    # each real provider is its own adapter file under /apps/ai-service/providers/,
    # implementing the same interface, so removing a provider is deleting one file
}
```
At least one real provider must be fully integrated, tested against real garments, and passing the QC gate before this system is considered complete — the mock provider exists for CI and local development only, it is not an acceptable end state for the shipped product.

### 8.7 Crest/logo compositing
The generative model never draws the crest. Pipeline:
1. Generate the base image (model, pose, scene) with the crest area masked out or absent.
2. Detect body/garment keypoints on the generated image.
3. Warp the real crest asset (vector or high-resolution raster, sourced from the brand's asset library, never regenerated) onto the garment using the detected keypoints — a classical computer-vision warp (homography or thin-plate-spline), not a second generative pass, because this step must be deterministic.
4. Composite, then hand the composited result to QC scoring (Section 8.4) — QC evaluates what will actually be published, not the pre-composite generation.

- [ ] Every endpoint has request/response schemas enforced with Pydantic models.
- [ ] `qc-score` thresholds read from config, not hardcoded.
- [ ] At least one automated test per endpoint using real fixture images.
- [ ] At least one real generation provider integrated, tested end to end, and passing the QC gate on a real test garment.
- [ ] Avatar identity training tested end to end with a real reference photo set.
- [ ] Crest compositing tested against the golden set with `logo_position_score` ≥ 0.95 on the test cases.

## 11. Security

- TLS everywhere, including internal service-to-service traffic.
- All credentials sourced from a secrets manager in every deployed environment — never `.env` files outside local development, and Terraform provisions the secrets manager without ever committing secret values.

## 16. UX/UI — interaction patterns

### 16.1 Confirmation tiers
- **Low stakes, reversible** (re-run QC, change a filter): no confirmation, immediate action, toast on completion.
- **Medium stakes** (advance a step, edit a field): no confirmation dialog, but a 5-second undo affordance in the resulting toast.
- **High stakes, hard to reverse** (approve & publish, mark rights `cleared`, delete): `ConfirmDialog` with typed confirmation.
Classify every action in the product into one of these three tiers as an explicit build checklist, not a case-by-case judgment call per PR.

### 16.2 Optimistic UI
Only for medium-stakes actions where failure is rare and cheap to visually roll back (e.g. dragging a board card). Never for high-stakes actions — the user must see the real "publishing…" state, not a card that looks published before Shopify has confirmed it.

### 16.3 Toasts vs. inline errors
Toasts report the result of an action just taken. Inline, field-level errors report validation problems that must be fixed before proceeding. Never report a field-level validation error via toast.

- OpenAPI spec auto-generated, served at `/openapi.json`, human-readable version at `/docs` (Swagger UI or Redoc).
- API versioned via URL prefix (`/v1/...`) from the start, even with only one version at launch.
- Breaking changes require a new version prefix and a documented deprecation window for the old one; additive changes do not.

## 23. CI/CD pipeline

```
on: pull_request
  → lint (golangci-lint, ruff, eslint)
  → unit + integration tests (Go, Python, frontend)
  → build all three services
  → dependency scan

on: merge to main
  → all of the above
  → run migrations against staging
  → deploy to staging
  → run e2e suite against staging
  → (manual approval gate)
  → run migrations against production
  → deploy to production
  → smoke test against production (health check + one read-only e2e scenario)
```
Migrations run automatically against staging on every merge; the manual approval gate is required before touching production — never auto-deploy schema changes to production data for a client of this profile.

### 23.1 Definition of Done
- [ ] Full pipeline implemented and tested with at least one real PR through the whole flow.
- [ ] Manual approval gate confirmed to actually block.
- [ ] Rollback procedure documented and tested once against staging.

## 26. Build order (dependency-ordered, not calendar-ordered)

This is the order in which modules must be built because of what depends on what — not a schedule.

1. **Data model (Section 4)** and **repository/infrastructure scaffolding (Sections 19, 24)** — everything else depends on the schema existing and a working local dev environment.
2. **Auth & permissions (Section 5)** — every API endpoint after this point is gated by it.
3. **Core backend API for brands, collections, products, variants, source documents (Section 6)** — the data layer the rest of the product reads and writes.
4. **AI service: extraction and copy generation (Sections 8.1–8.2)** — needed before the board has real data to show.
5. **Frontend design system and shell (Sections 13–14)** — build once, before any screen, so screens don't each invent their own patterns.
6. **`/upload`, `/board`, `/board/product/[id]` (Sections 15.4–15.6)** — the core usable loop: get a product from a technical sheet onto the board and into an editable detail view.
7. **Image processing and golden set (Sections 8.3, 8.4, 15.6)** — QC cannot exist without a golden set to score against.
8. **QC scoring wired end to end (Sections 6, 8.4, 15.4)** — the quality gate that the rest of the pipeline depends on.
9. **Shopify integration (Section 10)** and **`/rights` (Section 15.7)** — publishing depends on both the QC gate above and rights clearance being enforceable.
10. **Avatar pipeline, generation provider integration, crest compositing (Sections 8.5–8.7, 15.10)** — depends on QC (step 8) already being solid, since generated content is held to the same gate as everything else.
11. **Notifications, asset search/embeddings, calendar/bottlenecks, provider benchmarking (Sections 9, 15.8, 15.9, 15.11)** — all depend on the core pipeline (steps 1–10) already producing real data to notify about, search over, and benchmark against.
12. **Settings screens, briefing assistant (Sections 15.12–15.13)** — administrative and supporting features layered on top of a working core.
13. **Observability, CI/CD hardening, security hardening, load testing, penetration test (Sections 11, 12, 18, 19, 23)** — run continuously alongside the above, but the final penetration test and load test happen against a feature-complete system, so they are the last gate before Section 25's system-wide Definition of Done is checked.

## 27. Open questions

These require a decision from the client or from Gathered's own business/legal side — no amount of additional specification resolves them:

1. Final `taxonomy_schema` field list — confirm with the client's product team.
2. Final extraction model choice (Section 8.1) — validate against real Catalan/Spanish technical sheets, not just benchmark scores.
3. Real image/video generation provider(s) — commercial terms, data processing agreement, and confirmation the provider can meet the EU-residency constraint for any data it touches even transiently.
4. Named client-side owner for golden set approval and QC threshold changes (Section 21).
5. Shopify production store access and the exact metafield schema the client's e-commerce team wants to keep or migrate.
6. Real SLA figures from the chosen generation provider, to validate against Section 20's performance targets.
7. Confirmation of the EU hosting provider and region for Terraform to target, including their specific encryption-at-rest and backup guarantees, to cite accurately in security documentation.
8. Whether a second brand is realistically expected — affects how much of the "multi-brand-ready, single-brand-configured" approach (Section 1.1) is worth validating now versus trusting the data model to hold up later.
